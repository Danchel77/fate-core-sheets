# HANDOFF.md — точка входа для нового чата

Этот файл читается **после** `project.md` и `design.md` и **до** любых изменений. Его задача — быстро ввести в курс дела, сохранить утверждённый визуальный язык и не выдавать несуществующее за готовое. Дизайн нового экрана — ожидаемая работа: его нужно предложить вариантами, а не копировать лист.

## 1. Где мы сейчас

- Продукт — Fate Core Character Service: веб-лист персонажа, список, конструктор и печать.
- **Веб-лист утверждён** 2026-11-15 и живёт в корне: https://danchel77.github.io/fate-core-sheets/
- **Следующий экран — список персонажей.** Он ещё не спроектирован и не написан.
- Репозиторий: React 19 + TypeScript + Vite 6, чистый CSS. Публикация — GitHub Pages.
- Сейчас в коде **есть только одна страница `/`** с демо-героем.
- Сейчас **нет**: роутера, хранилища, списка персонажей, конструктора, печати/PDF, загрузки портрета, экспорта/импорта, сеттингового выбора на листе. Не выдавай их за готовые.

## 3. Жёсткие правила, чтобы не «изобретать»

- **Утверждённый лист заморожен.** Палитра, шрифты, заголовки, компоновка листа, блоки и токены не пересматриваются без прямой просьбы пользователя. Новый экран — не «переизобретение»: его компоновка, карточки и новые компоненты проектируются заново в утверждённом языке.
- **Продуктовые решения — не молча.** Открытый вопрос о поведении, объёме, хранении, маршруте или функции закрывается 1–3 вопросами пользователю. Внешний вид нового экрана решается иначе: покажи 3 временных варианта и дай выбрать. «Не придумывай „красиво“ молча» означает «не выпускай в продакшен без выбора», а не «не предлагай варианты».
- **Новые страницы, маршруты, хранилище, библиотеки и анимации не добавляются** без решения в `project.md`. Экран, который пользователь прямо заказал (сейчас — список персонажей), уже разрешён к дизайну и необходимым компонентам; маршруты, хранение и сторонние библиотеки всё ещё требуют отдельного решения.
- **Временные страницы сравнения.** Для нового элемента можно сделать 3 варианта на отдельной странице, показать **в реальном масштабе** и после выбора удалить страницу, её CSS, маршрут и тестовые данные.
- **Никаких постоянных тестовых страниц** (`src/preview`, `#test`, `#variants` и т. п.) в финале.
- **Не подменяй факты.** Перед ответом «готово» проверь код, сборку и живой сайт.
- **Пользователь — не программист.** Вопросы и объяснения — коротко, по-русски, без технического жаргона.

## 4. Архитектура в двух словах

```
src/App.tsx                 → SheetScreen (единственный экран)
src/screens/SheetScreen.tsx → собирает лист из блоков
src/components/             → блоки листа и общие элементы
src/data/demoCharacter.ts   → единственный демо-герой, без сохранения
src/styles/tokens.css       → единственный источник цветов, шрифтов и размеров
```

- `CharacterBlock` принимает `character: Character`; остальные блоки (`SkillsEditor`, `StuntBlock`, `StressBlock`, `ExtrasBlock`) получают начальные значения через props, но держат собственное состояние.
- При переключении персонажа монтируй лист/блоки с `key` по `id` (или сбрасывай состояние), иначе поля останутся от предыдущего героя. `FatePoints` уже сбрасывается по `initial`.
- `demoCharacter` не имеет `id`, `setting`, дат и хранилища. Целевая запись описана в `project.md` §5.2 как **ориентир**, а не готовый контракт.
- Старые хэш-страницы удалены; `App.tsx` очищает любой хэш и показывает корень.

## 6. Следующий экран: список персонажей

### Что известно
- Он стоит **до** конструктора и печати (решение пользователя 2026-11-15).
- Список должен показывать сохранённых персонажей и позволять перейти к листу.
- Хранилище в проекте ещё не подключено; архитектурный план — IndexedDB, но это не реализовано.
- Макет списка **не утверждён**. Не переноси декор листа в карточки автоматически.

### Что нужно спросить у пользователя до кода (по 1–3 вопроса)
1. **Откуда персонажи в первой версии:** только демо-примеры; создаются в этом же браузере и сохраняются; или пока без сохранения?
2. **Что показывает карточка:** имя и портрет; сеттинг; концепция/проблема; уровень и Обновление; дата изменения. Что из этого обязательно?
3. **Какие действия нужны:** создать, открыть, удалить, дублировать, экспорт/импорт. Что входит в первый экран?
4. **Маршруты:** одна страница со списком и листом-состоянием или отдельные адреса вида `#/characters` и `#/character/:id`? Библиотека роутера не установлена.
5. **Состояния:** пустой список, первый запуск, удаление, мобильный вид. Показать 3 варианта компоновки страницы и/или карточки в реальном размере списка.

### Рекомендуемый первый шаг (не решение за пользователя)
- Сначала закрыть вопросы, которые влияют на текущий шаг (минимум: откуда персонажи и что на карточке), записать ответы в `project.md` §7.1. Действия и маршруты можно уточнить после выбора компоновки.
- Затем показать **3 варианта в реальном масштабе**: если неясна структура страницы — 3 компоновки списка; если структура ясна — 3 карточки. Не ограничивай себя одной карточкой, когда вопрос в странице.
- После выбора — собрать список, пустое состояние и переход к листу. Конструктор не начинать.

### Технические грабли
- Нет `id` и `setting` в текущем `Character`; список потребует `CharacterRecord` (см. `project.md` §5.2).
- Нет сохранения: после перезагрузки всё пропадёт, пока не подключено хранилище. Не обещай сохранность.
- Портреты — URL демо-файла; загрузка/кадрирование не реализованы.
- Нет роутера: любой новый маршрут — отдельное решение, не «заодно».
- Не возвращай удалённые тестовые страницы ради проверки; временные файлы держи в `.scratch` и удаляй.
